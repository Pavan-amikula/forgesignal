# ForgeSignal research and design notes

Research checked 24 October 2026. This document separates external findings from project design decisions. References inform an independent implementation; they do not imply affiliation or endorsement.

## Dataset: what can actually be demonstrated

The **AI4I 2020 Predictive Maintenance Dataset** contains 10,000 synthetic observations and six input features: product quality type, air temperature, process temperature, rotational speed, torque, and tool wear. UCI labels the overall machine failure and five failure modes as targets, and UID/Product ID as identifiers. The dataset is available under **CC BY 4.0**, requiring attribution. Recommended citation: *AI4I 2020 Predictive Maintenance Dataset [Dataset]. (2020). UCI Machine Learning Repository. DOI: 10.24432/C5HS5C.* [UCI dataset, variables, provenance and license](https://archive.ics.uci.edu/dataset/601/ai4i%2B2020%2Bpredictive%2Bmaintenance%2Bdataset).

**Project decisions inferred from that schema:** train on the six inputs only; exclude `Machine failure`, `TWF`, `HDF`, `PWF`, `OSF`, and `RNF` from predictors to prevent direct target leakage. Drop UID and Product ID to avoid learning arbitrary identifiers. Predict the failure state associated with the current observation, rather than claiming a future failure horizon or remaining useful life. A streamed replay supplies a working real-time application, but is not live factory telemetry or field validation. [UCI target definitions and synthetic generation](https://archive.ics.uci.edu/dataset/601/ai4i%2B2020%2Bpredictive%2Bmaintenance%2Bdataset).

**Evaluation recommendations:** split before fitting transformations; keep a locked test partition; tune thresholds on validation data; compare a dummy classifier, logistic regression and a tree ensemble. Report average precision, ROC AUC, precision, recall, F1 and the confusion matrix, together with split sizes and failure counts. Because temperatures are generated with a random walk, an ordered holdout would be a useful robustness check. The delivered implementation compares a prior dummy and histogram gradient boosting with a random stratified split; logistic regression and an ordered holdout remain extensions. These are engineering recommendations, not guarantees from the dataset. [UCI generation description](https://archive.ics.uci.edu/dataset/601/ai4i%2B2020%2Bpredictive%2Bmaintenance%2Bdataset).

## Research papers translated into implementation choices

| Primary source | Finding | ForgeSignal design implication |
|---|---|---|
| Lewis et al., **Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks**, NeurIPS 2020 | Combines a language model with retrieved non-parametric knowledge. | Retrieve maintenance reference passages and attach source identifiers to responses. A local TF-IDF retrieval baseline is an engineering adaptation, not a reproduction of the paper's trained dense retriever. [Paper](https://arxiv.org/abs/2005.11401) |
| Yao et al., **ReAct: Synergizing Reasoning and Acting in Language Models**, ICLR 2023 | Studies interleaving reasoning and actions that access external sources or environments. | Use a bounded tool workflow: inspect machine telemetry, retrieve references, assemble evidence, and propose an action. Expose tool names, inputs, outcomes and a concise rationale; do not present a deterministic workflow as an autonomous ReAct LLM. [Paper](https://arxiv.org/abs/2210.03629) |
| Es et al., **Ragas: Automated Evaluation of Retrieval Augmented Generation**, 2023; revised 2025 | Separates retrieval relevance, faithful use of context and generation quality in RAG evaluation. | Maintain a labeled retrieval question set with expected source IDs. Report retrieval hit rate separately from LLM faithfulness. Do not label source-ID matching or deterministic template checks as RAGAS scores; real RAGAS scoring requires its actual metric implementation and configured dependencies. [Paper](https://arxiv.org/abs/2309.15217) |

## Related projects reviewed

**Azure Search + OpenAI demo:** a Python-backed RAG application over documents, with citations, supporting content, evaluation material and monitoring. Its own README warns that production deployment requires additional security work. ForgeSignal takes the product pattern of inspectable evidence and separate evaluation artifacts, while keeping a runnable local path and explicit provider configuration. No Azure sample code or sample company documents are required. [Official Azure sample](https://github.com/Azure-Samples/azure-search-openai-demo).

**Microsoft Real-Time Intelligence for Operations accelerator:** combines manufacturing telemetry, dashboards, anomaly detection and a conversational data agent. This validates the usefulness of an integrated operations workflow as a reference architecture. ForgeSignal's proposed distinction is a compact local incident-to-maintenance loop with reproducible benchmark reports and a visible approval step; this is a design choice, not a claim of superiority to the accelerator. [Official Microsoft accelerator](https://github.com/microsoft/real-time-intelligence-operations-solution-accelerator).

## Interface references and original design direction

**Grafana:** its dashboard guidance emphasizes a clear operational question, progressive drill-down, meaningful colors, understandable units and an intentional refresh cadence. Use a fleet summary that answers “which asset needs attention?”, an asset detail view with labeled sensor units, and a compact incident queue. Keep service rate/errors/duration available as engineering observability. [Grafana dashboard best practices](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices/).

**IBM Carbon data tables:** supports sorting, filtering, expandable detail and row actions. Use a dense asset table with a toolbar and a predictable selected-asset detail region. **Carbon status indicators:** pair severity with text and shape, and reserve attention-grabbing indicators for meaningful changes. Use “Healthy”, “Watch” and “Critical” labels alongside visible markers so color is not the sole signal. [Carbon data tables](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines), [Carbon status indicators](https://www.carbondesignsystem.com/building-blocks/core/patterns/status-indicators).

**Original visual direction:** graphite navigation, warm off-white work surfaces, restrained copper accents, thin technical dividers, tabular numerals, and red/amber reserved for operational severity. Prioritize readable telemetry, an evidence panel and an approval timeline. This palette and composition are project decisions; the references above supply interaction principles rather than copied layouts or assets.

## Framework and observability references

- **LangGraph** supports stateful workflows mixing deterministic steps with model-driven steps, including persistence, streaming and human oversight. Use explicit graph nodes and a genuine `StateGraph` implementation where installed; document any deterministic fallback separately. [Official overview](https://docs.langchain.com/oss/python/langgraph/overview).
- **MCP Python SDK** exposes typed tools/resources/prompts and client/server transports. At research time, upstream documentation describes v2 and a rename from `FastMCP` to `MCPServer`. Match code to the pinned major version: v1 code importing `mcp.server.fastmcp` needs `mcp<2`; v2 uses `mcp.server.mcpserver`. Do not implement a tool-shaped HTTP endpoint and describe it as tested MCP interoperability. [Official repository](https://github.com/modelcontextprotocol/python-sdk), [official migration guide](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/migration.md).
- **Prometheus** recommends query counts, failures and latency for services handling immediate requests. Instrument API requests and prediction duration; expose bounded labels rather than per-request or arbitrary user labels. A scrapeable endpoint demonstrates instrumentation; production monitoring additionally requires a configured scraper and retention. [Official instrumentation guidance](https://prometheus.io/docs/practices/instrumentation/).

## Evidence and attribution policy

Keep dataset attribution in the repository and README. Attribute external papers and projects used as references. Report only metrics emitted by reproducible runs and distinguish local benchmark results, simulated telemetry, optional cloud integrations and deployed integrations. Demo maintenance procedures are authored demonstration content, not manufacturer-approved operating instructions. These are project documentation decisions to keep the portfolio verifiable.
